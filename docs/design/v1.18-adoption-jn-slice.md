# Design: v1.18 adoption — JN slice (the centerpiece)

Status: **proposed** · Scope: `judicial-network` ·
Hub: `ledger/docs/design/v1.18-adoption-and-write-gating.md` (full Parts A–C) ·
Sibling: `attesta/docs/design/v1.18-adoption-sdk-slice.md`

The JN is where the **gating** work lands: it is the **preventative gate**
("is this valid?"). This slice records the verified current state and the
migration. The rule: **keep the gate, replace what backs the seam.**

---

## Verified current state (the gaps)

- **Flow is build → sign → submit** (`api/exchange/handlers/entries.go:10-15`):
  the exchange custodies the key, builds via SDK builders, signs, and forwards to
  the ledger. *"Refusing to sign is the only place we can prevent a write the
  ledger would otherwise accept and persist forever"* (`entries.go:22-26`).
- **The gate attests nothing.** `BundleSubmitGate` (`handlers/submit_gate.go`)
  holds **no signing key**; its `CosignatureVerdict` is transient and discarded;
  it forwards the **original entry bytes verbatim** (`handlers/entries.go:379-383`,
  `bytes.NewReader(body)`).
- **Authorization is self-asserted** — the security gap. `PayloadRoleResolver`
  reads the submitter's own `signed_by_capacities` block with **no chain walk**
  (`verification/payload_role_resolver.go:58-82`); the optional `delegation_ref`
  is not walked.
- **C1 ✅ DONE** (`7730701`) — attesta `v1.15.0 → v1.18.0`, non-regressive.

The `SubmitGate` shape (`CheckCosignature` + `RoleResolver` + prerequisite walker)
is the right seam. Only its **backing** is wrong.

---

## The two axes (JN owns Axis 1)

| Axis | Question | JN's role |
|---|---|---|
| **Gating** | **"Is this valid?"** | The JN gate runs the SDK authority engine and emits a cryptographic approval. |
| **Payment** | **"Can you pay?"** | Not the JN's concern — the ledger's Mode A (credit) / Mode B (PoW). |

These stay **cleanly separated**: the gate decides validity; the ledger decides
cost. (A per-log policy *may* let the gate's approval also satisfy payment — an
explicit bridge, not an implicit coupling.)

## Migration

- **C2 — SDK-backed `RoleResolver`; delete self-assertion (the real zero-trust
  fix).** New `verification.RoleResolver` whose role/capability is **proven** from
  SDK-verified delegation chains: `VerifyDelegationProvenanceWithTrust` /
  `EvaluateAuthorityWithTrust` (fed by the shared `LogTrustProvider` over the
  ledger's served tiles/proofs) → `attestation.EvaluateConstraintOverChain` +
  `RequiredLeafAttributes` — **never the entry payload**. Delete
  `PayloadRoleResolver`, the `signed_by_capacities` parsing, and the home-grown
  chain resolvers. The `SubmitGate` shape is unchanged.
- **C3 — rotation-aware key resolution (the DID change, JN side).** Resolve the
  signer's key **as-of the entry position** via `verifier.VerifyKeyAtPosition` over
  a `[]RotationRecord` projection (shared libs client) before trusting a signature.
- **C4 — as-of authority + cross-log.** Evaluate authority **as-of the entry's
  anchor position** (`EvaluateAuthorityWithTrust`), not "latest"; resolve cross-
  jurisdiction / forked references via `anchor.MultiLog` over the federated
  provider. This makes "every forking scenario = existing primitives" real.
- **C5 — capabilities as opaque attributes.** Declare required capabilities as
  `types.AttestationConstraint.RequiredLeafAttributes` (opaque `key=value`); the SDK
  matches them. The JN authors **no role vocabulary** in the rule engine — it
  declares data; the SDK enforces.
- **C6 — gate signs the write-authorization (Axis-1, the write-path fix).** The
  `BundleSubmitGate` gains a **rotatable Web3-EOA admission key** (it holds none
  today — this is the one new key). On `Admit` success it produces a **detached**
  signature over `H(canonical(entry))` **bound to the entry's as-of anchor**, and
  forwards the **unmodified** entry bytes plus the signature **out-of-band** (HTTP
  header). The ledger verifies it against the on-log admission keyset and **drops
  it** (never stored). The gate's key is published in the `admission_authority_v1`
  on-log keyset.

### Why Web3 EOA (not Ed25519, not EIP-1271) — on evidence
The gate is a **named actor**; named actors are Web3 IDs. An **EOA secp256k1**
key is verified by local `ecrecover` (~tens of µs) and is EVM-verifiable —
**scalable and verifiable** at 1K+ TPS. Ed25519 is not EVM-verifiable (no
precompile); an EIP-1271 contract key needs an `eth_call` per write (the SDK's
`did/eip1271_cache.go` is deliberately batch-scoped/block-pinned) — not viable on
the hot path. Multi-party gate control = a **K-of-N set of EOAs**, not a contract.

## Surviving the two-part submission
The ledger submits in two parts (synchronous SCT promise; async sequencing). The
gate's authorization binds **entry content + as-of anchor**, both fixed at
build/sign — so it remains valid through async sequencing (authority is pinned to
the anchor, not the assigned position). The ledger verifies it **before** issuing
the SCT promise; the **auditor** re-derives the same verdict as-of the anchor from
the final log. The gate's signature is the real-time chokepoint; the log is the
durable proof. We never store — or trust — "the gate said so."
